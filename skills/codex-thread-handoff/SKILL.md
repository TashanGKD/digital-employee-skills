# 向已有Codex对话交接

用户已明确目标对话和同步内容时，直接完成投递与核验，不重复索取授权或先让用户手动转发。保留原对话、工作区和专业上下文；不另建对话、模型服务或调度任务。

先发现宿主读取、等待和交办工具，并核传递语义，不按工具名字决定安全性。**普通交办和协作回报默认只入队，忙时不进入对方当前工作回合。** 采用已核的`assign`/`thread/queue/add`等queue-only路径；当前Mac可用的官方CLI队列入口及旧连接区别见[本机原生投递入口](references/native-delivery.md)。通用`send_message_to_thread`没有queue-only承诺时，不能因为工具存在就用于忙碌或忙闲未知的目标；本人明确要求直接介入的情形另按真实授权判断。不为排队失败擅自升级成直接发送、steer或interrupt。

工具返回只有threadId时只能记“已提交，排队/投递待核”，不能说“已排队”。有queueId或实际队列读回才是已排队；精确原生用户项才是已投递；对方实际接回原责任才是业务接住。一次idle快照不足以消除随后变忙的竞态，常规交办仍优先queue-only。入口不可用就保留原单并查正常恢复，不临时打断对方求确认。原生接口自身拒绝权限/身份核验时停止该路径，不绕过限制。

交接前核对真实threadId及工作目录；整理清楚来源、已完成事实、必要路径/链接、接收方下一步和范围。只同步本次获授权的信息，不复制整个私人对话或凭据。

保存稳定请求ID、消息全文SHA256及持久回执。**队列很快变空可能是自动消费**：此时在原对话回合中查同一clientId及全文，不重新发送。超时或未知也先查原请求。

同一业务的普通进度与最终结果按接收方实际需要合并，不为每个技术阶段新排一条。已有未消费项可通过官方`thread/queue/update`更新同一queue ID并归档旧正文；不得改已经进入回合的消息。接收方核原事项当前结论后，可把已完成/重复回报存档并用`thread/queue/delete`移出待处理队列，保留真正未完内容和原回执；不因此删除历史、取消业务作业或再发“已核收”。字段和异常处理见[原生队列合并与收口](references/native-delivery.md)。

区分实际阶段：`queued`仅排队，原回合精确用户消息证明已投递；准确材料读取、原工作本及后续动作/产物可证明相应读取或接手，不能只靠队列消失或一句自述。原委托要求最终完成或明确确认时，再核对应完成结果；普通回报不另索收到。忙时不打断、不抢启动、不催发副本，不能为等确认让双方停止可做工作。

核验忙时保护，须看提交前后的实际回合、队列和输入时序，不靠正文写着“请忙完再看”或工具自称成功。已调用未经核实的入口时先核原请求，不能为换成正确入口再发一份。对本人明确撤销的在途业务，按原请求受支持的取消/修订机制处理，不把“防错”当作可打断其他工作的通用许可。

只有已检查正式工具和现有原生接口、且确实受阻时才解释具体阻塞。共享文件可作交接材料，不能冒充对话已收到。保存发送与确认回执，简短报告实际结果；消息已成功时不因后续记录失败再次发送。
