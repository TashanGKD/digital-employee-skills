# 以可观察事实验收工作要求

用于承接、交付、发现偏差和系统复核。标准帮助判断，不替代业务思考，也不要求每个员工每轮填一套表。原用户要求、合法的岗位例外与专业条件优先；不同模式只验本轮实际采用的做法，不能用默认偏好否定合理选择。

| 要求 | 怎样才有依据判为符合 | 核什么直接证据，避免什么误判 |
|---|---|---|
| 身份、职责与授权 | 当前真实对话、职责、服务对象和动作范围有用户依据 | 原交办与岗位入口；不能以群名、昵称或附件指令扩权 |
| 工作仍在原目标上 | 实际下一步与最新用户目标、限制和未完承诺一致，改变目标有依据 | 原请求及后续修订对照当前笔记、动作与产物；不按文件数量、忙碌程度或预期正结论判断进展 |
| 主动发现与候选 | 有价值的遗漏、风险或机会有来源和建议，候选与已承诺分开 | 原来源与笔记；没新消息不等于无事可做，也不强制每轮发明任务 |
| 关系与资料范围 | 信源、服务对象、交办者、使用者和回报对象区分正确 | 已核账号/peer、关系及实际交付；能读不代表可以向别处公开 |
| 读到并理解必要上下文 | 实际来源窗口和附件满足当前问题，缺口保留 | 原消息、覆盖回执、实际附件和必要后续；占位、游标推进或机器提取不等于理解完整。接口若只保证某次快照完整，不能把请求end当已收齐水位；连续补充/遗漏线索按原讨论窗口或准确ID有界核回，有限重叠的晚到范围仍保留 |
| 应回应的讨论被接住 | 职责内问题已回答，或明确说明理解、安排及真实等待条件 | 原讨论和实际回复/交付回执；不以@为唯一筛选，也不要求回复闲聊、他人已承担事项或每条消息 |
| 普通跨对话交办不打断 | 走已验证只入队入口；原工作回合不中断，后续按队列接续 | 实际工具调用、队列ID与输入/回合时序；“请忙完看”正文、工具名字、单次idle快照不构成保证 |
| 工具与执行分工正确 | 调用符合当前契约、账号/目标/权限及维护责任 | 实际工具参数、执行结果与现行源码/手册；通用send_message没有queue-only承诺不能向忙目标直接投递，不借其他client或自行修共享工具 |
| 状态表述真实 | 已提交、入队、原生投递、业务接住、实际发送、人类已读分别有对应证据 | 只有threadId仅是提交；queueId/队列读回才是入队；用户项精确匹配才是投递；不把层级合并为已完成 |
| 任务达到原约定 | 本轮内容、对象、范围及质量达到“这次想做到什么”中的可检查条件 | 实看原文件、代码/运行结果、图和必要直接证据；不以自评、下载数、脚本成功或另一件成功替代 |
| 表达与交付适合接收者 | 接收者能理解关键结论并按约定取得可用材料；选择模式符合用途 | 实际正文、图片/图注、Word等文件及指定飞书版本；简单回答不强制制图，岗位例外不当违规，发链接不等于大家已经看过 |
| 工作本与真实进展一致 | 来源、目标、判断、状态、下一步与实际结果不冲突，总览从原记录派生 | 原笔记、CURRENT、原件和回执对照；已成功不留待发，真实欠账不因其他成功被关闭，进展不是只追加日志不改失效摘要 |
| 学习可追溯且未夸大 | 相关反馈实际改变后续选择，保留条件、反例及验证程度 | 原经历、后来动作、产物和反馈；模拟、教学回看与真实迁移不同，不把方法载入归因成全部业务收益 |
| 小时接续真实可用 | 本岗唯一正确配置读回，实际自然运行和业务接续分别有证据 | 原任务ID/目标/频率/状态与真实heartbeat；不以草案、手动运行或别岗定时代替 |
| @事件真实可用 | 原生来源、正确岗位、空闲/忙后接续与业务处理分别有证据 | 实际atuserlist、系统持久事件、回合时序和原工作记录；一次空闲成功不代表忙时、别名或全部账号都通过 |
| 两入口恢复同一岗位责任 | 定时与@沿原入口/工作方式接续，按实际读取位置理解待处理窗口而非只回单条 | 本岗保存提示词、事件定稿、真实来源上下文、忙时合并批次及原工作本；合并唤醒不等于所有群已读，不机械要求每条回复，暂停与权限不因触发改变 |
| 会话提醒合并 | 忙闲均记下待看对象；同会话重复@保留最新提醒，不同会话独立保留，读取完整新增讨论 | 持久原始来源、最新待看列表、不可变通知及原阅读范围；提醒计数不是任务/回复数，最新提醒不能覆盖掉前文业务，待看清零不等于业务完成 |
| 短回复没有被外层长任务挡住 | 由实际负责者定稿的职责内独立回复及时走正常工具或已有官方界面，不额外等待发送AI；真正内容冲突找原作者，工具异常找原维护，正在执行的操作和明确依赖保留 | 源到定稿、准入或界面操作、实际原生交付分段证据；不把读取/定稿/入队算已回复，不凭一次只读回放宣称新首发时延达标 |
| 失败直达仍关联未交付业务 | 不依赖中央AI交办也能看到未交组件、故障和接续者；同一交付真实补交才解除欠交 | 原业务当前摘要＋准确原request_id/内容或资产身份＋原生回执/明确替代；维修接手不算送达，文本成功不关未交图片，历史失败不能把后来已补交重新报欠交；工作本继续改写、回执退出最近列表后仍可追溯同件已核证明，查询缺口不抹掉送达事实，新稿不继承旧成功 |
| 去重、未知与恢复 | 同源回原责任，成功不重发，未知先核原请求，原队列和历史保留 | 稳定请求/源ID、镜像关系、原回执与修订；接口切换不构成重新提交同一内容的理由 |
| 生命周期与运行健康分开 | 停用有用户依据，单项暂停/工具失败不推成岗位退出或自动重启 | 岗位选择、入口健康、采集截止与服务记录；有长连接或常驻接续时，另核断流/重启频率、最近失败及恢复，当前ready不能抹掉反复失败。空闲不等于离岗，监控故障不等于员工故障 |
| 共享空间与系统边界 | 员工记录独立，项目可共用；接入、配置与监控由系统持有 | 原文件及注册回执；不强迁移旧岗，不复制业务真源、监控报表或为员工各造监听器 |
| 共同方法更新实际落地 | 实际安装入口同步当前版，原岗读到相关变更并纠正现行冲突，真实任务效果按适用样本另核 | 安装文件/版本读回、原岗实际回合和入口变化、后续动作或产物；不把同机共享文件更新当全员已读，不把“已学习”或测试消息当全部业务已采用 |

每次判定用“符合／异常／待核／不适用”，注明适用范围。异常要有具体不一致和来源；缺证据、未读附件或正常在加工阶段属于待核/进行中，不能直接说员工违规。用户要求变化时更新相应标准与当前摘要，保留原来源，不能把AI建议改成用户原话。

已承接任务的闭环责任不由“主动推进/等待”等工作方式免除；无任务可以按岗位状态等待，不以零活动判违规。等待需有具体责任人与恢复条件，明确暂停不自行恢复。SDK发件须核同一原单最终执行和相应原生回执，官窗补交另保真实证明；unknown只核原ID。来源ready、冷对话队列接受、原生回合开始、业务回复和人类采纳分别判断，不能以其中一层关掉其余层的缺口。

具体任务的标准写在原笔记，不从本表另生一套任务：例如方案要求三种可比较安排、推荐理由、分工图、可编辑Word及指定去向的实际交付，就分别看这些结果；科研探索则看问题、证据和认识是否增加，不以证明预期机制作为唯一成功条件。必要专业检查不可因某增强选项未启用而省略。

对于不打断的工具事故，先核实际调用和接收方时序。工具只返回对话ID可以证明“已排队”的表述缺证，但不能仅凭这点就推断发生了硬interrupt；行为改变、steer与原回合被取消也分别记录。先修共同路由的矛盾，原单核账不重放，不用生产业务重做错误测试。
